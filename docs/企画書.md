# かんせいのパレット 企画書

## 1. 企画概要

「かんせいのパレット」は、白黒の世界で回路タイルを回してつなぎ、世界に色を取り戻していくブラウザ向けパズルゲームです。2日間のゲームジャムに、1人で参加して開発します。

| 項目 | 内容 |
| --- | --- |
| タイトル | かんせいのパレット(英題: KANSEI PALETTE) |
| プロジェクト名 | kansei-palette(CMakeなどは kansei\_palette) |
| ジャンル | 回路つなぎパズル(タイルを回して電気を通す)。マリオパーティのミニゲームのような、短くて直感的なテンポ |
| テーマ | 「かんせい」 |
| プラットフォーム | Webブラウザ(PC・スマートフォン)。itch.io にHTML5ゲームとして提出 |
| 開発言語・技術 | C++ / raylib / Emscripten(WebAssembly) |
| 開発体制 | 1人 |
| 開発期間 | 2026年9月25日(金)から2日間 |
| プレイ時間 | 全3ステージとエンディングで約5〜10分 |
| 対象 | ジャム参加者、審査員、itch.io の一般プレイヤー |
| 入力 | マウスのクリック、タッチのタップ(補助としてキーボード) |
| 言語 | 日本語 |

### 企画の目標

1. テーマ「かんせい」を、ゲームの仕組みと物語の両方で回収する。
2. 説明を読まなくても、最初のタップで遊び方が分かる。
3. ステージクリアの瞬間に、色が戻る演出で爽快感を出す。

### テーマ「かんせい」の解釈

| 同音異義語 | ゲーム内での回収 |
| --- | --- |
| 完成 | 回路を完成させる(ステージ単位)。世界の色を全部そろえて完成させる(ゲーム全体) |
| 感性 | 主人公が、色を感じ取る力を取り戻す |
| 歓声 | 色が戻った瞬間の喜びを、光と音で表す |

### 参考: Webプロトタイプ

ルールと演出の手触りを先に確かめるため、three.js製のWebプロトタイプを作成済みです([プロトタイプ](https://claude.ai/artifact/MrTGYhpnb9d6KgfAiHK5rR))。本書の数値と仕様は、このプロトタイプの実装値に合わせています。本番のC++/raylib版は、このプロトタイプを仕様の見本として実装します。

## 2. コンセプトと世界観

色を失った主人公が、回路をつなぐことで世界の色を一つずつ取り戻し、最後にタイトル画面まで色づくことが、このゲームの物語です。

### ストーリー

- 主人公は、世界の色が見えない。世界は最初、白黒です。
- 回路をつなぐと、電気が通ったタイルから色がにじむ。
- ゴールを全部光らせると、そのステージの色が世界に戻り、箱庭の建物や木がせり上がる。
- 全ステージをクリアすると、白黒だったタイトル画面が色づき、主人公ははじめて世界の色を見る。

### 色の復元の二段構造

| 単位 | 内容 | 目的 |
| --- | --- | --- |
| タイル単位 | 電気が通ったタイルが、電源から近い順に色づく | パズル途中でも進んでいる実感を出す |
| ステージ単位 | ゴールを全部つなぐと、そのステージの色相が世界全体に永続的に戻る | 達成感と、次のステージへの動機を作る |

### 段階的に戻る色

色は色相(赤・青・黄緑)で区切って戻します。ステージ1で赤、ステージ2で青、ステージ3で黄と緑が戻り、最終ステージで全色がそろいます。同じ素材を白黒と彩色の2種類用意せず、彩度の制御だけで実現します。

### 差別化ポイント

1. タイトル画面を含め、ゲーム全体が「未完成から完成へ」の体験になっている。
2. 色相ごとの復元で、赤い屋根・青い噪水など、物の色が一つずつ先に目を引く。
3. 固定カメラの3D箱庭と、手描き風の2Dスプライトを組み合わせたHD-2D風の見た目。

### 表現上の配慮

現実の色覚異常は、ほとんどの場合完全に色が見えないわけではありません。ゲーム内の説明やストアページでは「色を失った」「色が見えない」という表現にとどめ、「色盲」という言葉は使いません。パズルは色に依存せず、形だけで解けるようにします。

## 8. 技術仕様

本番は C++ と raylib で作り、Emscripten で WebAssembly にビルドして itch.io に提出します。プロトタイプ(three.js)で決めたルールと演出を、同じ数値で raylib に移します。

### 技術スタック

| 項目 | 選定 |
| --- | --- |
| 言語 | C++17 |
| ライブラリ | raylib(最新の安定版を確認して固定。記憶では決めない) |
| Webビルド | Emscripten(emsdk の最新安定版を確認して使う) |
| ビルド | CMake。ネイティブとWebの両方を同じCMakeListsでビルドする |
| 提出形式 | index.html と .js / .wasm / .data を zip にして itch.io に HTML5 としてアップロード |
| 追加ライブラリ | なし(Box2D、Dear ImGui、EnTT は使わない) |
| フォント | ライセンスを確認した日本語フォント(使う文字だけに絞って埋め込む) |

セットアップ手順と、DxLibからraylibへの関数対応表は、別で作成した引き継ぎメモ(handoff.md)の依頼内容として渡しています。

### プロトタイプから raylib への対応

| やりたいこと | プロトタイプ(three.js) | raylib での実現方針 |
| --- | --- | --- |
| 固定カメラ | PerspectiveCamera(縦視野角 32度、俯角 50度) | Camera3D(fovy 32、CAMERA\_PERSPECTIVE)。カメラ位置は注視点から俯角と距離で計算 |
| 床に寝たタイル | 平面にテクスチャ | GenMeshPlane のモデルにテクスチャを設定し、DrawModelEx でY軸回転 |
| 立ち絵 | 足元基準のビルボード | DrawBillboardPro(足元を origin で指定)。傾きの0.9倍ではなく完全にカメラへ向けてよい |
| 光と星くず | 加算合成 | BeginBlendMode(BLEND\_ADDITIVE) |
| 色の復元 | ShaderMaterial(色相で判定) | フラグメントシェーダー。Webは GLSL ES 100、ネイティブは 330 を用意。uniform は 復元度(vec3)と通電度(float) |
| タイル選択 | 平面との交差でマスを求める | GetMouseRay と y=0 の平面の交差。交点の x, z から行と列を求める |
| バネ | 自前のバネ | 自前で実装(バネ強さと減衰は前章の値) |
| 音 | WebAudio | InitAudioDevice を最初のクリック後に呼び、LoadSound / PlaySound |
| フォント | Google Fonts | LoadFontEx で、使う文字のコードポイントだけを指定 |
| タッチ操作 | ポインターイベント | マウス互換として動く想定。実機で確認する(未検証) |

### 色の復元をシェーダーでできない場合の保険

Webでシェーダーが動かないと、ゲームの核が崩れます。ジャム開始前に、簡単なシェーダーをWebで動かして確認します。動かない場合の代替案は次のとおりです。

1. 読み込み時に全画像のグレー版を作り(ImageColorGrayscale)、テクスチャを二種類持つ。
2. 小物・タイルごとに、グレーと彩色をクロスフェードする(色相単位ではなく、物単位の復元になる)。

この場合、「赤だけが先に戻る」という演出はできなくなるため、ステージごとに物を割り当てて彩色化する形に変更します。

### ソース構成(提案)

| ファイル | 役割 |
| --- | --- |
| main.cpp | ウィンドウ作成、メインループ(Webは emscripten\_set\_main\_loop、ネイティブは通常のループ) |
| game.cpp / game.h | 状態進行(タイトル、プレイ、クリア演出、クリアカード、エンディング)。Update と Draw を分ける |
| board.cpp / board.h | タイル、回転、通電判定(幅優先探索)、クリア判定。描画に依存しない |
| stages.h | ステージデータ(章 4 の記法の文字列)と、戻る色、小物の配置 |
| config.h | カメラ、バネ、演出の数値(章 5 の表)。調整はここだけで行う |
| assets.cpp / assets.h | 画像、音、フォントの読み込みと、ファイル名一覧 |
| render.cpp | 盤面、小物、主人公、地面の描画。色の復元シェーダーの設定 |
| fx.cpp | 星くず、輪、フラッシュ、カメラ揺れ |
| ui.cpp | タイトル、HUD、クリアカード、ボタン |
| audio.cpp | 効果音の再生と、最初のクリック後の初期化 |

判定ロジック(board)を描画から分けておくと、ステージデータの検証を単体でできます。

### Webビルドで気をつけること

| 項目 | 対応 |
| --- | --- |
| メインループ | while ループを使わず、フレーム関数を emscripten\_set\_main\_loop に渡す |
| ファイル | 実行時にファイルを開いても見つからない。--preload-file で assets を埋め込む |
| オーディオ | 自動再生制限。最初のクリックを待ってから鳴らす |
| スレッド | 使わない |
| シェーダー | GLSL ES 100(#version 100)と精度指定を使う |
| 画面サイズ | itch.io の埋め込みサイズに合わせ、リサイズに追従する(カメラ距離を縦横比で調整する式はプロトタイプにある) |
| メモリ | テクスチャは合計約140万ピクセル(RGBAで約5.6MB)で、問題ない見込み |

### 性能目標

60fps。描画対象は、タイル25枚、小物最大 10、主人公1、星くず最大700粒で、すべて軽い見込みです。Webで重い場合は、星くずを400粒に減らします。

## 10. スケジュール、リスク、スコープ外、未決事項

最大のリスクは、初めての raylib と Emscripten でシェーダーと日本語フォントがWebで動かないことです。初日の午前に、この2点を真っ先に検証します。

### スケジュール(2日間)

| 時間帯 | 作業 | ここまででできていること |
| --- | --- | --- |
| 1日目 午前 | emsdk と raylib の環境、ネイティブとWebのビルド。日本語フォントと、色の復元シェーダーをWebで確認 | ブラウザで日本語が出て、画像が色相単位で彩色化できる |
| 1日目 午後 | 3D盤面とタイルの表示、回転、通電判定、クリア判定、ステージ1 | ステージ1を解ける |
| 1日目 夜 | ステージ2・3、ロックタイル、HUD、タイトル→ ステージ → エンディングの通し | Must がすべて動く(最低ライン) |
| 2日目 午前 | 色の復元とクリア演出(光、星くず、せり上がり)、主人公のアニメ、効果音 | クリアが気持ちよい |
| 2日目 午後 | エンディングの色づき、スマートフォン確認、Webビルドの最終確認、itch.io へのアップロード | 提出可能な状態 |

1日目の夜に Must が通しで動いていない場合は、演出を削って通しを優先します。途中の段階でも、ネイティブ版だけは常に動く状態を保ちます。

### リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 初めての raylib / Emscripten でビルドに詰まる | 初日がつぶれる | ジャム前に空のプロジェクトをWebで動かす。公式テンプレートに従う |
| 色の復元シェーダーがWebで動かない | ゲームの核の演出が崩れる | 初日午前に検証。代替案(グレーと彩色のクロスフェード)を用意する |
| 日本語フォントが出ない、または重い | 文字が豆腐になる、読み込みが遅い | 使う文字だけに絞って埋め込む。初日午前に確認 |
| 音が自動再生制限で鳴らない | 音のないゲームになる | 最初のクリック(「はじめる」)で初期化する |
| スマートフォンで重い、タッチが効かない | スマートフォンで遊べない | 早めに実機で確認。星くずを減らす。パソコンを主対象にして許容する |
| AI生成画像がジャムのルールに合わない | 提出資格や評価に影響 | 開始前にルールを確認。不可なら、図形と文字だけの代替見た目、またはフリー素材に切り替える |
| ビルボードの見た目がプロトタイプと変わる | 見た目の不一致 | 完全にカメラへ向ける形で妥協する |
| スコープが膨らむ | Must が未完成になる | Could は2日目午後の余った時間だけにし、先にパズルを完成させる |
| 主人公の画像に隣のポーズの破片が残る | 見た目のノイズ | 残ったフレームを取り除くか、使わない。待機・走り・喋びを優先して整える |
